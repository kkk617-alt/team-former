# PRD — 팀 프로젝트 팀 편성 웹 앱

## 1. 배경과 목적

팀 프로젝트의 팀을 교수가 일방적으로 짜면 학생의 역할 선호가 반영되지 않고, 학생에게 전부 맡기면 역할 구성이 한쪽으로 쏠린 팀이 생긴다. 이 앱은 **학생이 스스로 팀을 만들되 앱이 규칙을 강제하고, 끝까지 팀을 못 구한 학생만 AI가 배정하는** 절충안을 구현한다.

목표는 다음 세 가지다.

1. 학생이 팀을 고르고 기존 팀원의 동의를 얻어 들어가는 절차를 앱이 중개한다.
2. 팀 구성 규칙(인원, 주 역할 중복, 필수 포함 역할)을 사람의 판단이 아니라 앱이 검사한다.
3. 모집 마감 뒤 남은 학생을 AI가 배정하되, **AI의 답을 믿지 않고 앱이 규칙으로 재검사**한다. AI가 실패하면 앱이 스스로 배정한다.

세 번째가 이 과제의 핵심이다. AI는 보조 수단이고, 정답을 보증하는 주체는 앱의 규칙 엔진이다.

## 2. 사용자

| 사용자 | 하는 일 |
| --- | --- |
| 학생 | 학번·비밀번호로 로그인. 팀 목록과 팀원의 주/보조 역할 조회. 팀에 지원. 내 팀에 들어온 지원에 찬성·거부 투표 |
| 관리자(교수) | 학번 `admin` 으로 로그인. 명단 CSV와 팀 수로 상태 초기화. 모집 마감. 마감 뒤 AI 배정안 확인·확정 |

앱에 등장하는 학생은 모두 명단 CSV의 **가상 학생**이다. 실제 사람의 이름이나 학번은 명단, 코드, 문서, 화면 어디에도 쓰지 않는다.

## 3. 용어

- **주 역할** — 학생마다 정확히 1개. 팀 안의 중복을 따지는 기준.
- **보조 역할** — 학생마다 0~2개. 필수 포함 역할을 맡을 수 있는지 따질 때만 쓴다.
- **담당 가능 역할** — 주 역할과 보조 역할의 합집합.
- **필수 포함 역할** — 기획자와 웹 프로그래머. 모든 팀에 서로 다른 사람으로 1명씩 있어야 한다.
- **막힘** — 앱이 지원을 아예 접수하지 않은 것. DB에 기록하지 않는다.
- **거절** — 접수되어 대기 중이던 지원이 떨어진 것. 팀원의 거부, 승인 직전 검사, 모집 마감이 원인이다.

역할은 6개다: 기획자, 웹 프로그래머, 프론트엔드 디자이너, 테스터, 보고서 작성자, 발표자.

## 4. 팀 구성 규칙

확정된 팀 구성이 만족해야 하는 조건이다.

| 규칙 | 내용 |
| --- | --- |
| 인원 | 모든 팀이 2~4명. 빈 팀이 없다 |
| 주 역할 중복 | 주 역할이 같은 학생이 한 팀에 2명 이상이면 안 된다 |
| 필수 포함 역할 | 모든 팀에 기획자 역할 학생과 웹 프로그래머 역할 학생이 **서로 다른 사람으로** 1명씩 있어야 한다. 주 역할로든 보조 역할로든 맡을 수 있다 |

필수 포함 역할은 한 학생이 둘 다 담당 가능해도 **하나로만 센다**. 기획자를 맡을 수 있는 학생 1명만 있는 팀은 필수 포함 역할 2개 중 1개만 채운 것이다. 이는 팀원 집합과 `{기획자, 웹 프로그래머}` 사이의 **최대 이분 매칭** 문제이고, 앱은 그 매칭 크기로 충족 여부를 판정한다.

## 5. 기능 요구사항

### 5.1 로그인

학번과 비밀번호로 로그인한다. 비밀번호는 bcrypt 해시로만 저장하고 평문은 어디에도 남기지 않는다. 학번만으로는 남의 계정에 들어갈 수 없고, 비밀번호가 틀리면 로그인되지 않는다. 학생 계정으로는 관리자 기능을 쓸 수 없다. 구글 로그인(`st.login`)은 쓰지 않는다. 채점자가 학생 여러 명으로 번갈아 로그인해야 하기 때문이다.

### 5.2 명단 올리기 (관리자)

명단 CSV와 팀 수를 넣으면 앱 상태가 초기화된다. 지원·투표·팀원·마감 표시를 모두 지우고, 명단의 학생과 넣은 팀 수만큼의 빈 팀을 만든다. 관리자 계정은 명단을 다시 올려도 남는다.

CSV 는 BOM 이 붙은 UTF-8 일 수 있으므로 `utf-8-sig` 로 읽는다. 열은 `student_no,name,main_role,sub_roles` 이고 보조 역할이 2개면 `;` 로 구분한다.

### 5.3 지원

학생이 팀에 지원한다. 다음 경우에는 **막힘**이다.

| 사유 | 판정 시점 |
| --- | --- |
| 모집이 마감됨 | 단추를 숨기거나 비활성화 |
| 이미 팀에 속함 | 단추를 숨기거나 비활성화 |
| 결과를 기다리는 지원이 있음 | 단추를 숨기거나 비활성화 |
| 팀이 꽉 참 (4명) | 단추를 누른 뒤 안내 |
| 같은 주 역할의 팀원이 있음 | 단추를 누른 뒤 안내 |
| 필수 포함 역할을 맡을 학생의 자리가 모자람 | 단추를 누른 뒤 안내 |

마지막 항목의 판정식은 다음과 같다. 지원자가 들어간 뒤의 팀을 `예상팀원` 이라 하면

```
남는자리 = 4 - |예상팀원|
충족수  = 예상팀원과 {기획자, 웹 프로그래머} 의 최대 매칭 크기
미충족  = 2 - 충족수
남는자리 < 미충족  →  막힘
```

부등식이어야 한다는 점이 중요하다. 미충족이 2 라도 남는자리가 2 면 막지 **않는다**. 아직 두 자리로 두 역할을 채울 수 있기 때문이다.

### 5.4 투표

| 상황 | 결과 |
| --- | --- |
| 빈 팀에 지원 | 투표할 팀원이 없으므로 바로 승인 |
| 팀원이 있는 팀에 지원 | 대기. 그 팀의 팀원 모두가 투표한다 |
| 모든 팀원이 찬성 | 승인 |
| 한 명이라도 거부 | 다른 팀원의 투표를 기다리지 않고 바로 거절 |

투표할 사람은 **투표하는 때의 팀원**이다. 내가 지원한 뒤에 다른 지원자가 먼저 승인되어 팀원이 되면 그 사람도 내 지원에 투표한다. 한 번 투표하면 바꿀 수 없다.

### 5.5 승인 직전 재검사

모든 팀원이 찬성해 승인하려는 순간에 규칙을 **다시** 검사한다. 같은 팀에 대기 중인 지원이 여럿일 때 앞의 지원이 먼저 승인되어 팀 구성이 바뀌기 때문이다. 재검사에서 인원·주 역할 중복·필수 포함 역할 자리를 어기게 되면 그 지원은 거절된다. 그 전에는 대기 중인 지원을 미리 거절하지 않는다.

처리 순서는 지원한 순서가 아니라 **투표가 끝난 순서**다.

### 5.6 마감과 배정

1. 관리자가 모집을 마감한다. 그 뒤로는 지원과 투표를 할 수 없다.
2. 마감 때 대기 중인 지원은 거절된다. 1명뿐인 팀의 학생은 팀에서 빠져 "팀이 없는 학생"이 된다.
3. 관리자가 AI 배정을 누르면 앱이 현재 팀 구성, 팀이 없는 학생과 그 역할, 규칙을 AI에게 보내 배정안을 받는다. 배정은 팀이 없는 학생만 팀에 넣으며 **이미 팀에 있는 학생은 옮기지 않는다**.
4. 앱이 배정안을 다섯 가지로 검사한다: 팀이 없는 학생이 빠짐없이 배정됨, 한 학생은 한 팀에만 배정됨, 모든 팀이 2~4명, 팀 안에서 주 역할 중복 없음, 필수 포함 역할 충족.
5. AI가 응답하지 않거나 빈 응답·오류를 내거나 4항의 검사를 통과하지 못하면 2차·3차 모델로 넘어간다. 모델 하나를 부른 때부터 응답을 다 받을 때까지 **120초**가 넘으면 끊는다.
6. 3차 모델까지 실패하면 앱이 스스로 배정한다. 4항의 검사 다섯 가지를 모두 통과하는 배정을 모든 경우를 따져 끝까지 찾는다.
7. 검사를 통과한 배정안만 관리자에게 보여 준다. 관리자가 확정하면 DB에 저장한다.
8. 규칙을 모두 지키는 배정이 아예 없으면 배정안을 만들지 않고 그 이유를 보여 준다. 이때는 AI를 부르지 않는다.

### 5.7 학생 화면

팀 목록에서 로그인한 학생의 팀을 구별되게 표시한다. 팀이 없으면 그 사실을 보여 준다. 이미 투표한 지원에는 찬성·거부 단추를 숨기거나 비활성화하고 내가 어떻게 투표했는지 보여 준다.

### 5.8 다른 사람의 변경 보기

다른 학생의 지원이나 투표가 화면을 다시 열지 않아도 나타나야 한다. `st.fragment` 로 바뀐 부분만 5초 간격으로 다시 그린다.

## 6. 비기능 요구사항

| 항목 | 요구사항 |
| --- | --- |
| 결과 안내 | 모든 동작의 결과를 `승인` / `대기` / `거절` / `막힘` 중 하나로 시작하는 문장으로 보여 준다 |
| 화면 요소 이름 | 공고 2.7절의 Streamlit `key` 를 그대로 쓴다. 자동 채점 프로그램이 이 이름으로 요소를 찾는다 |
| DB 연결 | 연결은 한 번만 만들어 재사용한다. 질의마다 새로 만들면 화면이 몇 초씩 느려진다 |
| 비밀 값 | 오픈라우터 키, DB 주소, 관리자 비밀번호는 `.env` 와 Streamlit Secrets 에만 둔다. 화면과 로그에 출력하지 않고 코드에 적지 않는다 |
| 응답 시간 | AI 배정 전체가 10분을 넘기지 않는다. 모델 3개 × 120초 = 최대 6분 |
| 시각 표시 | 배포 서버는 UTC 이므로 화면에는 한국 시각으로 바꿔 보여 준다 |

## 7. 범위에서 빼는 것

- 학생이 역할을 직접 고르거나 바꾸는 기능. 역할은 명단 CSV 가 정한다.
- 팀 이름 변경, 팀 해체, 팀장 지정.
- 확정 뒤 팀 구성 수정. 확정은 마지막 단계다.
- 구글·소셜 로그인.
- 기존 팀원을 다른 팀으로 옮기는 재배치. 배정은 팀이 없는 학생만 다룬다.

## 8. 성공 기준

1. 부록 연습용 시나리오 3개(쉬움 6단계, 중간 11단계, 어려움 15단계)를 순서대로 실행했을 때 모든 단계의 결과 안내 첫 단어가 기대 결과와 같다.
2. 확정한 팀 구성이 4절의 규칙 세 가지를 모두 만족한다.
3. AI 모델 3개가 모두 실패해도 앱이 규칙을 지키는 배정을 스스로 찾아낸다.
4. 로그인하지 않은 브라우저로 배포 주소를 열면 로그인 화면이 보인다.
5. 저장소 어디에도(커밋 기록 포함) 키와 관리자 비밀번호가 없다.
