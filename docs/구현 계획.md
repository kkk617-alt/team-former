# 구현 계획

## 1. 설계 원칙

### 1.1 규칙 엔진을 DB·화면과 분리한다

채점 30점 중 24점이 시나리오 점수이고, 시나리오 점수는 전부 "결과 안내의 첫 단어가 기대 결과와 같은가"로 결정된다. 그래서 규칙 판정을 **DB도 Streamlit도 모르는 순수 함수**로 떼어 냈다.

이렇게 하면 Supabase와 오픈라우터 키 없이도 부록 시나리오 3개의 모든 단계를 `pytest` 로 재현해 기대 결과를 미리 맞춰 볼 수 있다. 규칙을 화면 코드 안에 두면 이 검증이 불가능해지고, 배포한 앱을 손으로 눌러 보는 것 외에 확인할 방법이 없어진다.

### 1.2 AI의 답을 신뢰하지 않는다

`app/ai.py` 는 모델을 부르고 JSON 을 파싱하는 일만 한다. 그 결과가 맞는지는 `app/assign.py` 가 `app/rules.py` 의 같은 검사 함수로 판정한다. AI 경로와 자율 배정 경로가 **같은 검사 함수**를 통과해야 하므로, AI가 그럴듯한 오답을 내도 확정되지 않는다.

### 1.3 경쟁 조건은 앱이 세지 않고 DB가 막는다

"마지막 자리에 두 명이 동시에 들어감"을 앱에서 인원을 센 뒤 넣는 방식으로 처리하면, 두 요청이 같은 순간에 세면 둘 다 들어간다. `tf_members` 의 `(team_id, slot_no)` 기본 키와 `student_id` 유일 제약이 이를 DB 수준에서 막는다.

## 3. 규칙 엔진 설계

### 3.1 담당 가능 역할

```python
담당가능(학생) = {학생.주역할} | 학생.보조역할
```

주 역할은 팀 안의 중복을 따지는 기준이고, 보조 역할은 필수 포함 역할 충족 여부를 따질 때만 쓴다. 두 용도를 섞지 않는다.

### 3.2 필수 포함 역할 충족 판정

팀원 집합과 `{기획자, 웹 프로그래머}` 사이의 **최대 이분 매칭** 크기를 구한다. 역할이 2개뿐이므로 일반적인 매칭 알고리즘 대신 경우를 직접 따진다.

```
기획자가능 = {s | 기획자 ∈ 담당가능(s)}
웹프로그래머가능 = {s | 웹 프로그래머 ∈ 담당가능(s)}

둘 다 비어 있지 않고, 서로 다른 사람을 하나씩 뽑을 수 있으면  → 2
한쪽만 비어 있지 않거나, 같은 한 사람만 양쪽에 있으면         → 1
둘 다 비어 있으면                                            → 0
```

"서로 다른 사람을 하나씩 뽑을 수 있다"는 `기획자가능 ∪ 웹프로그래머가능` 의 크기가 2 이상인 것과 같다.

한 학생이 두 역할을 다 담당할 수 있어도 1로만 세는 것이 핵심이다. 기획자이면서 보조로 웹 프로그래머인 학생 혼자 있는 팀은 충족수 1 이다.

### 3.3 지원 게이트

순서대로 검사하고 처음 걸리는 사유를 돌려준다. 순서가 곧 안내 문구의 우선순위다.

1. 모집 마감 → `막힘: 모집이 마감됨`
2. 이미 팀에 속함 → `막힘: 이미 팀이 있음`
3. 결과를 기다리는 지원이 있음 → `막힘: 결과를 기다리는 지원이 있음`
4. 팀이 꽉 참 → `막힘: 팀이 꽉 참`
5. 같은 주 역할의 팀원 → `막힘: 같은 주 역할의 팀원이 있음`
6. 필수 포함 역할 자리 모자람 → `막힘: 필수 포함 역할을 맡을 학생의 자리가 모자람`

6번의 판정식:

```
예상팀원 = 팀원 ∪ {지원자}
남는자리 = 4 - |예상팀원|
미충족  = 2 - 충족수(예상팀원)
남는자리 < 미충족  →  막힘
```

**부등식이어야 한다.** 부록 2(중간) 8단계에서 팀4 는 학생11(RW) 혼자이고 충족수가 0 인데, 학생12 가 지원하면 예상팀원 2명·남는자리 2·미충족 2 이므로 `2 < 2` 가 거짓이라 막히지 **않는다**(기대 결과: 대기). 반면 부록 3(어려움) 11단계에서 팀3 은 학생11·학생15 로 충족수 0 인데 학생14 가 지원하면 예상팀원 3명·남는자리 1·미충족 2 이므로 `1 < 2` 가 참이라 막힌다(기대 결과: 막힘). 두 단계가 서로를 검증하는 쌍이므로, "필수 역할이 없으면 막는다" 같은 단순 구현은 통과할 수 없다.

### 3.4 승인 직전 재검사

`flow.py` 가 승인을 시도할 때 3.3 의 4·5·6 을 팀의 **현재** 상태로 다시 돌린다. 1·2·3 은 지원 접수 시점의 조건이므로 재검사에서 제외한다. 걸리면 그 지원을 `거절` 로 바꾸고 사유를 `reason` 에 남긴다.

### 3.5 확정 팀 구성 검사

모든 팀에 대해 인원 2~4, 주 역할 중복 없음, 충족수 2 를 확인한다. 배정안 검사의 3·4·5항이 이 함수를 그대로 쓴다.

## 4. 동시성

승인은 한 트랜잭션 안에서 처리한다.

```
BEGIN
  SELECT ... FROM tf_teams WHERE id = %s FOR UPDATE      -- 팀 단위 직렬화
  팀원·대기 지원 조회
  rules.승인직전재검사()
  통과하면  INSERT INTO tf_members (team_id, slot_no, student_id)
            slot_no = 비어 있는 가장 작은 번호
  UPDATE tf_applications SET status = ...
COMMIT
```

`INSERT` 가 유일성 위반으로 실패하면(같은 순간에 다른 요청이 그 자리를 차지) 예외를 잡아 그 지원을 `거절` 로 처리한다. 앱이 세는 인원은 참고용이고, 최종 판정은 DB 제약이 한다.

## 5. AI 모델 체인

### 5.1 모델당 전체 120초

`requests` 의 `timeout` 인자는 **다음 바이트를 기다리는 시간**만 재므로, 응답이 천천히 조금씩 오면 전체 시간은 120초를 훨씬 넘길 수 있다. 그래서 `stream=True` 로 받으면서 청크마다 경과 시간을 확인하고, 마감 시각을 넘기면 연결을 끊는다.

```
마감 = 시작 + 120
for 청크 in 응답.iter_content():
    if 지금 > 마감:  연결 끊고 '시간초과' 로 기록, 다음 모델
    버퍼에 쌓기
```

### 5.2 실패로 보는 경우

HTTP 오류(429 포함), 빈 응답, JSON 형식 오류, 시간 초과, 그리고 **배정안이 검사를 통과하지 못한 경우**를 모두 실패로 보고 다음 모델로 넘어간다. 추론 모델이 생각하는 데 토큰을 다 써서 빈 응답을 내는 일이 잦으므로 `reasoning.effort = low` 와 넉넉한 `max_tokens` 를 함께 보낸다.

`openrouter/free` 라우터는 쓰지 않는다. 다음 모델로 넘어가는 처리를 직접 만드는 것이 과제의 일부다.

### 5.3 진행 안내

`assign_status` 컨테이너에 몇 차 모델의 응답을 기다리는 중인지와 경과 시간을 보여 준다. 모든 호출은 `tf_ai_logs` 에 모델명·차수·상태·소요 시간으로 남겨, README 7.1절 5항의 실패 사례를 꾸며 내지 않고 실제 기록으로 제시한다.

## 6. 자율 배정 (3차 모델까지 실패)

미배정 학생을 팀에 넣는 백트래킹 탐색이다. 채점 시나리오의 미배정 학생은 8명 이하, 팀은 4개 이하로 탐색 공간이 작다.

가지치기:

- 팀 인원이 4를 넘으면 중단
- 팀 안에 주 역할이 겹치면 중단
- 남은 자리 수가 그 팀의 미충족 필수 역할 수보다 적으면 중단 (3.3의 6번과 같은 식)

남은 학생을 다 넣은 뒤 최종 검사를 통과하면 그 배정을 돌려준다. 끝까지 찾지 못하면 "규칙을 지키는 배정이 없음"과 이유를 `assign_status` 에 보여 준다.

탐색 순서는 **담당 가능 역할이 적은 학생부터** 배치한다. 선택지가 좁은 학생을 먼저 넣으면 막다른 길을 일찍 발견해 탐색이 빨리 끝난다.

## 7. 화면

### 7.1 결과 안내 보존

`st.fragment` 가 5초마다 화면을 다시 그리므로, 단추를 누른 결과를 지역 변수에 두면 다음 갱신에서 사라진다. 결과 문장을 `st.session_state` 에 넣고 `result` 컨테이너가 그것을 읽어 그린다.

### 7.2 화면 요소 이름

공고 2.7절의 `key` 를 상수로 한곳에 모아 쓴다. 표와 다르게 지정하면 자동 채점이 멈추고 5점이 깎이므로, 이름을 코드 여러 곳에 흩어 적지 않는다.

`refresh` 단추는 공고상 쉬운 해결 전용이지만 함께 둔다. 채점 프로그램은 이 단추가 있으면 동작 전에 먼저 누르므로, `st.fragment` 자동 갱신이 한 번 엇나가도 채점이 멈추지 않는 보험이 된다. 어려운 해결은 `st.fragment` 로 구현되어 있다.

## 8. 작업 순서

| 순서 | 작업 | 검증 방법 |
| --- | --- | --- |
| 1 | `roles.py`, `rules.py` | 부록 시나리오 3개 32단계를 인메모리로 재현하는 pytest |
| 2 | `assign.py` 자율 배정 | 어려움 시나리오 마감 직후 상태에서 규칙 만족 배정을 찾는지 |
| 3 | `roster.py` | 나눠 준 CSV 3개를 BOM 유무 양쪽으로 파싱 |
| 4 | `schema.sql`, `db.py`, `repo.py` | Supabase 에 실행하고 왕복 질의 |
| 5 | `flow.py` | 실제 DB 로 지원·투표·마감 흐름 |
| 6 | `ai.py` | 일부러 없는 모델명으로 실패·전환 확인 |
| 7 | `ui/` + `streamlit_app.py` | 로컬 실행 후 부록 시나리오 손으로 재현 |
| 8 | 배포 | 로그인하지 않은 브라우저로 배포 주소 열기 |

1~3 단계는 DB와 키 없이 할 수 있으므로 먼저 끝낸다. 규칙이 틀린 상태로 화면을 만들면 어디가 틀렸는지 찾기 어렵다.

## 9. 비밀 값 취급

`config.py` 는 `.env`(로컬)와 `st.secrets`(배포)에서 값을 읽고, 값의 존재 여부만 "있음/없음"으로 보고한다. 값 자체를 화면이나 로그에 쓰지 않는다. `.gitignore` 가 `.env` 를 걸러 내고, `.env.example` 에는 자리표시자만 둔다.
